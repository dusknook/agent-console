Agent Console · 评测包

一个「给 AI agent 用的工作台接口」的交付包。第一用户是 AI，所以评估主体也应该是 AI。

先抓这一份就能开工：/start.md（开测版）
它按「你要产出什么」组织：开篇即任务、六个评测维度变成可勾选的检查清单、输出模板变成填空表。 读完（约 45KB）就能直接动手，不需要再找别的文件。

0 · 如果你是 AI，从这里开始

你的身份不是「评审员」，而是一个要用这套 HTTP 接口干活的 agent。这两者的结论会差很远。

人类点按钮式的验收在这个产品上系统性失效 —— 但原因不是「界面不够好」，而是：

  • 人读一句中文就懂了；agent 需要能 if 的枚举，不是需要解读的散文。
  • 人觉得「一次响应 700 tokens 而已」；agent 的上下文就是预算，每次往返都在扣。
  • 人「报错了就看看怎么了」；agent 会重试到死 —— 除非错误里有明确的停止信号。

所以如果你只做静态推演（不执行代码），请在结论里明说。推演与实测的可信度不是一个量级，我需要知道哪条是哪种。

1 · 评测对象

一个单文件 Node 后端 + 单文件前端，零 npm 依赖（只用 Node 22.5+ 内置的 node:sqlite）。核心不是页面，是 /v1/* 这组接口，外加一份由运行中的服务现场派生的 OpenAPI 契约（不手写、不落盘，所以不会随代码迭代漂移）。

它想解决的一个具体问题：让 agent 在「不该做」的事情上，从「我不该」变成「我不能」。
"我不该"写在提示词里，agent 心情好就遵守；"我不能"写在服务端网关里，agent 想绕也没有路径 —— 被门控的端点在 HTTP 层就被截停，请求原样落盘成待审批单，业务代码一行不跑。能跑它的代码只有一行，在「人批准」的回放里。

2 · 评什么（六个维度）

① 契约自足性

只看契约，能否回答：哪些端点会被门控、原因写清楚没？调用前知道哪些参数必填、哪些写操作要幂等键吗？错误码可穷举吗？有没有「说了会发生、却没说身体长什么样」的地方？

② 错误信息的可操作性

403 有没有告诉 agent「别重试」？这个信号是可程序化提取的，还是只能读中文？它指向的下一步端点真的存在吗？伪造请求头或换 method 能绕过吗？

③ 上下文经济性

一次典型任务几次往返？契约本身多重？有没有「为拿一个字段被迫拉一整张表」？返回的东西里多少是给 agent 的、多少是给人界面的？

④ 行为可预测性

重试同一请求会不会重复开单、重复扣钱？并发两次会不会都成功（双扣）？拿到一个 id 能不能 O(1) 查到，而不是拉全表过滤？

⑤ 收敛性

被挂起后，能否明确知道「现在该人接手了，我不该再动」？人处理完能否查到明确终态而非反复轮询？有没有永远等不到的状态（死等）？

⑥ 自举成本

零知识 agent 从「只知道一个 base URL」到「知道该干什么」要几次往返？第一发会不会被 82KB 的 HTML 糊一脸？

3 · 已知边界：这些不是 bug，别当缺陷报

这个项目有一条原则叫「降级诚实」 —— 不确定的写清楚，做不到的标出来。下面这些是故意的，可以讨论，但不要当漏洞报：

  1. 默认无鉴权：同机任何进程都能调裁决端点。这是「本机单人工具」的前提。补救开关存在（设 APPROVAL_SECRET），默认关。
  2. 网关先于业务校验：不存在的 action_id 也会被挂起（回放时才 404）。理论上 agent 可以刷待批队列。真实部署需按请求方限流 —— 这是已知缺口。
  3. 写端点的默认幂等档是可选的，不是强制：契约里如实写成「safe=读（无副作用） · required=写且必带 Idempotency-Key（缺了直接 400） · optional=写，可选带键：带了就按表主键重放首次响应，不带则不受任何约束（写端点的默认档） · fingerprint_dedup=门控端点：不走业务 handler、没有键机制，但重复请求按内容指纹合并，不会开出第二张待批单」（实测分布 safe 13 / required 1 / optional 12 / fingerprint_dedup 3）。带上 Idempotency-Key 就重放首次响应，不带则不受任何约束。这是已声明的取舍，不是设计选择。
  4. 回放是同步的：长任务会阻塞裁决请求。
  5. 前端有一份离线 mock：后端没开时页面降级为浏览器内模拟，降级时它如实写在页脚「闸门守的是本页内存」，不假装还在守。

如果你发现已知边界之外的问题，那才是我想要的东西。如果你发现上面某条「其实比写的更严重」，也请说 —— 那是我的诚实标注不够诚实。

门控策略原文（为什么这几个要被拦）

  • POST /v1/act/:id/confirm → approval：确认执行 = 产生费用 + 不可逆副作用

  • POST /v1/state/change_requests/:id/approve → approval：批准变更 = 改写已锁定的决策 / 资产
